# Explicit incident reconciliation — synthetic local-paper evidence contract

## Trust boundary (defined before implementation)

The v3 observation, acceptance receipt, ACK, ledger hash, a price touch, current/public order-book data, an operator narrative, and an arbitrary `resolved` flag are **not** evidence that an execution happened or did not happen. This slice accepts only a separate, immutable, previously committed **synthetic private local-paper execution journal** record, under a writer fence. Journal input is an explicit test fixture, not a live execution feed or production attestation. Its `source_kind` is fixed to `synthetic_private_paper_journal`; it has a unique bounded evidence ID, intent ID, one source identity and a contiguous per-intent source sequence starting at 1, and either an `EXECUTION` record with a unique source execution ID, BTC delta, USDT price, explicit USDT fee, execution time and bounded observed-fill aliases, or a `FINAL_COMPLETE` record listing the execution evidence IDs for this intent and an inclusive coverage watermark. Register evidence before the incident it supports; store canonical bytes, length and SHA-256 immutably in local SQLite, and chain the registration in the ledger. Reconciliation references the exact stored ID and digest, not caller-provided claims about its content. A digest binds stored bytes but does **not** authenticate a self-authored journal; use only for synthetic regression coverage until an independently authenticated execution source and complete negative coverage are specified.

One reconciliation ID refers to exactly one immutable incident (`fill_id` plus its original ledger hash) and one evidence reference (`evidence_id` plus its SHA-256), with the caller's expected ledger-head hash as the state revision. Every field and record has a fixed byte/count bound. The decision is one of `VERIFIED_EXECUTION`, `VERIFIED_NONEXECUTION`, `VERIFIED_DUPLICATE`; missing, contradictory or insufficient evidence produces **no** resolution. A stable reconciliation ID may be retried with identical content (return the durable result) but must conflict on changed content. A stale revision for a new ID fails. Writer fencing is checked within the same SQLite transaction.

`VERIFIED_EXECUTION` requires the journal execution record to identify the incident fill ID and match the original event's intent, UTC time, delta, price and fee. Apply only if the original event is a valid next cumulative fill on an open/pending intent. A proved spend can exceed admission budgets: record the actual signed cash, BTC quantity, proportional remaining cash/risk reservation and filled exposure; expose negative available cash or budget deficit rather than fabricating money. Verified corrections count toward the same 16 applied-fill storage limit as ordinary fills; at capacity, keep further evidence unresolved rather than claiming an effect that cannot be represented safely. Quantity overfill, contradictory cumulative, terminal corrections, pre-acceptance timing and full fill storage are **unsupported**, remain unresolved and block new risk until a separately specified auditable correction exists.

`VERIFIED_NONEXECUTION` requires a precommitted `FINAL_COMPLETE` journal record for the same intent, whose coverage ends at/after the alleged event timestamp, which names every execution evidence record for this intent and contains no alias for this incident. Journal execution aliases are unique across source executions for an intent; `(source_identity, source_execution_id)` is unique across all intents. Recovery rechecks both against the original immutable entries. Every already-applied fill covered by that watermark, including a prior verified correction, must match exactly one **distinct** listed source execution ID by alias and economic fields; two applied fills cannot consume one source execution. Absence from a partial query is not proof. `VERIFIED_DUPLICATE` requires one precommitted execution record linking this incident and a distinct *already applied* fill under the same source execution ID with matching time/delta/price/fee; a similar price or user-selected fill ID alone is insufficient. Both close the incident without new economics.

Resolution, original-incident reference, evidence reference, accounting delta, materialized closed status and a hash-chained ledger entry commit atomically. Original observations and journal bytes are never edited or deleted. Failed verification leaves them and every reservation untouched. New risk remains blocked in this bounded slice even after the final incident closes: closure is not an independently approved readiness transition. Outstanding incidents and negative cash/available cash are explicit; no auto-release of a cancellation reservation. Replay validates evidence linkage, decision semantics, identity and quantity conservation, global incident ordering, materialized cash/base/risk/deficits and all bounds. Historical v3 requires an explicit verified v3→v4 preservation migration; no operator database is migrated here.

## Remaining limits

No trusted independent paper execution or complete negative-coverage source exists in this repository. Synthetic journal tests demonstrate the *conditional accounting protocol*, not real-world verification or production readiness. Actual terminal overfill/cumulative correction, incident-resolution readiness, source authentication, external evidence retention, power-loss acceptance and real execution remain outside this slice.
