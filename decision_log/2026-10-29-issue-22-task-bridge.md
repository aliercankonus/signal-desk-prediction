## Proposed local contract

The operator explicitly supplies an outside-git private state directory; `doctor` is read-only and `once` is a single bounded attempt, not a loop. A nonblocking local process lock protects **one worker using one state directory on one machine**. The bounded, durable journal records issue number, body digest, pinned base, run ID, status, branch/worktree, timestamps, publication and result identities before/after each effect. It never contains credentials, raw issue comments, private configuration or unrestricted agent output. Keep no more than one active issue/worker; bound records, log bytes, retries, wall time and child lifetime. Do not reset, clean, stash or overwrite existing worktrees.

Persist the run identity, repository/issue number and `queued` state *before* any child starts. Verify the configured source repository and the actual pinned commit object before publishing progress. A bounded journal also records status transitions, timestamps, and the GitHub comment receipt IDs (or an explicitly unconfirmed publication). Restart after an ambiguous child invocation, push or publication blocks redispatch. Read-only reconciliation compares confirmed journal comment IDs and exact allowlisted payloads with comments from the authenticated publishing identity, plus the draft PR/head/CI and pinned-base ancestry; it never treats unconfirmed or counterfeit comments as proof, clears the block or authorizes retry. Reconcile branch, draft PR and exact head with read-only GitHub queries and require explicit operator review before any retry. Do **not** claim exactly-once execution of external effects. On timeout or interruption terminate the child process group, retain the run and mark it blocked. Publication failures likewise preserve a blocked state; never mark `review-ready` based only on a child assertion. A result is review-ready only after validating the draft PR URL/head against GitHub and publishing an allowlisted, redacted status. Status vocabulary is `queued`, `running`, `blocked`, `review-ready`, with run ID, pinned base, draft PR URL, exact head and exact-head CI when verified. Do not echo the issue body, secret values, private paths or raw child logs to GitHub.

The production Hermes adapter is separately verifiable against installed `--help` and leaves real execution for a later explicit operator action. A fake agent and fake GitHub API exercise the entire local state machine without network or host effects. There is no persistent activation in this proposal. Merge, deployment, privileged host operation, collector startup, operator-data migration and trading execution remain outside the worker's authorization; current deployment is unchanged.

## Manager review follow-up — moving target branch

The original `base` authorization pin is the immutable starting commit for the one worktree, **not** GitHub's `pr.base.sha`, which can lag behind the moving target tip of `main`. Verify the PR's target repository and exact `main` branch independently, read `refs/heads/main` for the currently observed target tip, and require a consistent comparison showing the pinned starting commit is an ancestor of the result head. The journal retains that pinned `base` plus the `target_tip` observed at result verification; read-only reconciliation keeps the journaled result separate from a newly observed PR/ref, even if no result was journaled. A later `main` update alone neither invalidates the authorized run nor re-dispatches it. Never substitute the moving target tip for the authorization pin. Synthetic regressions cover a stale PR base SHA after target drift, drift after review-ready, inconsistent ancestry evidence, unjournaled observations, disallowed targets and unrelated heads. No real issue #22 worker run is permitted by this follow-up.
