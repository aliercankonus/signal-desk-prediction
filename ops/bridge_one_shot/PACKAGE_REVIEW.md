The Actions workflow policy is enabled with `allowed_actions=all`. The worker is not excluded from changing an unprotected default-branch signer workflow/policy or its trigger code: the repo grants its account admin access and its classic credential includes `repo`/`workflow`; no write probe was performed. It can control repository content that such a workflow would consume. An Actions environment secret alone cannot make untrusted, worker-writable workflow code into a manager-only signing boundary. App provenance on a particular manager comment does not cure that code/secret access, and we cannot prove the worker cannot call a manager-only route using the shared account. No signer workflow, secret or instruction dispatcher is added while these facts remain true.

**Concrete missing capability for manager review:** enforce a protected, immutable-to-worker signer workflow/policy and secret boundary, plus manager-exclusive invocation. The worker's repository-admin/`workflow` credential must not be able to push to the trusted workflow ref, alter its protection/secrets or invoke the manager-controlled signing path. A separately managed protected environment and narrowly scoped manager automation may work only after those permissions are demonstrably separated; do not rely on author/login, App metadata, an approval flag or a human signature per instruction. Provisioning, secret storage and activation are separate approvals. If that separation cannot be made without replacing the existing credential/ownership model, stop the issue-comment signer option and request an independently trusted manager-side executor rather than weakening verification.
